# AGENTS.md

## Рабочий процесс (ATDD)

### 0. Общее правило
**После каждого этапа запрашивать согласование и ревью от пользователя и только потом продолжать.**

### 1. Acceptance Test (Красный)
- Написать **один** красный acceptance test (или доработать существующий, если изменение затрагивает проверяемый им флоу)
- Тест должен падать по правильной причине (некомпилляция — неправильная причина; тест должен компилироваться, но падать из-за неправильной реализации)
- **Важно:** После написания acceptance теста запустить его и убедиться, что он красный по правильной причине (получает неправильное значение, а не падает с ошибкой компиляции или NullPointerException)
- **Важно:** После проверки красного acceptance теста получить подтверждение пользователя, что тест корректен, прежде чем переходить к TDD циклу

**Важное правило:** При написании красного теста можно добавлять сигнатуры методов/классов, но НЕЛЬЗЯ писать их реализацию. Вместо реализации используется безопасное неправильное значение (например, `return ""`, `return 0`, `return false`, `return null`, если он не приводит к NPE). Исключения в заглушках не используются. Это гарантирует, что тест падает по правильной причине — из-за отсутствия логики, а не из-за отсутствия кода.
### Что создавать на фазе Red (красный тест)

**МОЖНО:**
- Пустые классы (без полей)
- Пустые методы с безопасным неправильным возвращаемым значением
- Сигнатуры методов (название, параметры, тип возврата)

**НЕЛЬЗЯ:**
- Поля классов
- Реализацию методов
- Конструкторы с инициализацией
- Вспомогательные методы
- **Любую реализацию до написания теста**

**Пример правильного подхода на фазе Red:**
```java
public class BankAccount {
public int balance() {
return 0;
}
}
```

**Пример неправильного подхода на фазе Red:**
```java
public class BankAccount {
private Money balance = Money.zero(); // НЕЛЬЗЯ

public void deposit(int amount) {
this.balance = this.balance.add(Money.of(amount)); // НЕЛЬЗЯ
}
}
```

### Частые ошибки при работе по TDD

❌ **Поспешил с реализацией** — написал код до того как тест упал
❌ **Добавил поля заранее** — поля создаются только на фазе Зелёный
❌ **Реализовал конструктор** — инициализация только когда тест требует

**Примечание:** Если доработка не меняет acceptance-флоу и проверяется на уровне unit-тестов, acceptance test можно не трогать.

### 2. TDD цикл (Unit-тесты)
- Предложить список маленьких TDD-тестов для реализации acceptance criteria
- Дождаться согласования пользователем
- Для каждого теста: написать → запустить и убедиться, что он красный по правильной причине → получить подтверждение пользователя → реализовать → запустить и убедиться, что он зелёный → получить подтверждение пользователя → при необходимости отрефакторить

**Важно:** После каждого TDD-теста и его реализации необходимо получить подтверждение пользователя, прежде чем переходить к следующему тесту.

**Важное правило:** Маленькие TDD-тесты НЕ должны дублировать acceptance тесты.
- Acceptance тест проверяет полный сценарий через сервис/контроллер (создание задачи, перевод в статус DONE, проверка duration)
- TDD тесты проверяют изолированные единицы: создают объекты руками через конструктор, мокают зависимости, проверяют конкретный метод
- Пример: TDD тест создаёт `TaskEntity` и `DateTimeProvider` вручную, вызывает `calculateDuration()` напрямую, без сервиса и БД

**Важное правило:** Пиши реализацию ТОЛЬКО для того, что покрыто TDD-тестом. Не добавляй лишнюю логику (минуты, часы, дни), пока нет соответствующего TDD-теста на каждый случай.

**Важное правило:** Нельзя писать в реализации методов код, на который ещё не написан тест. Каждый блок кода в реализации должен быть покрыт существующим тестом. Если нужна дополнительная логика — сначала напиши тест на неё.

### 3. Финальная проверка
- Прогнать все тесты
- Убедиться, что все тесты зелёные

**Важно:** После финальной проверки получить подтверждение пользователя о завершении задачи.
